# Recording splits and audio conversion

Planning checkpoint for the TAGnetic fork. Base is `0a1a4429`. The working roadmap puts conversion first, then recording splits on the same processing and progress workflow. This plan keeps that order for the shared processing work and makes the split editor the main user-facing deliverable. The save workflow and replacement proofs are recorded below.

## What people can do

| Use case | What TAGnetic would do and why it helps |
| --- | --- |
| Split a tape or live set by ear | Right-click one recording and choose **Split recording…**, or use the same command on the ribbon. Play the recording, place a marker at the playhead, and listen across the cut before moving on. This works on tapes with no track list or silence between songs. |
| Rip an album image with a CUE sheet | Open a CUE for the selected recording, or choose a CUE and confirm its master audio. TAGnetic fills in starting positions, titles and performers. The user can correct bad boundaries without editing the sheet by hand. |
| Split a tape with a Discogs listing | Pick the exact release and side, then set where it begins in this recording. TAGnetic places draft markers from the listed lengths and brings in the track names. Audition and adjust the proposals for tape speed, lead-in, side changes and differences between the release and the recording. |
| Tag a pack in one pass | Set shared fields and front artwork once. Give each track its own title, artist or other overrides. Preview the filenames and tags together so a wrong edition, duplicated name or missing title is visible before writing. |
| Convert or convert while splitting | Keep the master and export new MP3 or FLAC files. A separate **Convert audio…** command handles whole files using the same format choices, review and output checks. This covers cutting an MP3 tape rip into tagged MP3 tracks and splitting a FLAC master into MP3s for portable playback. |

## The editor

- Use a spacious modal with the recording name and total time at the top. Put a short overview above the main zoomable waveform. Put transport controls beside the playhead time and the cut actions close to the waveform. Use the current theme, focus outlines and dialog styling. At narrow widths the waveform and controls stay at the top, with the track list and shared tags below.
- Offer **Manual**, **Import CUE…** and **Use release tracklist…** in the same editor. Merge proposed markers only after showing what will change in the draft. Bring the user straight back to a playable waveform after importing.
- Provide play/pause, seek, zoom around the pointer or playhead, and jump to the previous or next marker. Let users add a cut at the playhead, drag it, or edit its exact time from the track list. Provide a short **Audition cut** loop across both sides of a marker. Offer keyboard equivalents and document them inside the dialog. Keep typing, IME, Tab and Escape scoped to the control that owns them.
- Put one row per output track below the waveform. Keep selection in the list and waveform in sync. Show order, name, artist, start and length. Apply tags in this order, from lowest to highest priority: saved master tags, accepted release or CUE defaults, accepted per-track suggestions, user-edited shared values, then user-edited per-track values. A per-track field can inherit, override or explicitly clear. Tell the user when library edits on the master are still pending. Compute output track numbering and lengths from the actual output ranges. Keep CUE or provider positions separately. Moving a cut keeps both tracks' tags attached to their stable track identities. Deleting a cut keeps the earlier track's tags and is reversible with draft Undo. Keep draft Undo separate from library Undo. Save and reopen an exact draft so a long set can be finished later.
- Allow cuts to be auditioned before the full waveform is ready. Show progress and errors inline and keep the editing controls available as soon as their data is ready. Restore focus to the entry point or the originating file row when the dialog closes. Keep the active source fixed even if selection elsewhere changes. The ribbon can offer **Choose recording or CUE…** with no selection. The split editor accepts one supported master and explains why it is unavailable for multiple files. Conversion can take the displayed ordered selection.
- End with **Review output**, then **Export tracks**. Show every destination name, format, range, final tags, missing data, and fields or artwork that the output format cannot represent. Offer **Export CUE** by itself for a user who wants to keep a single playable master. Warn before closing a changed draft and before discarding imported candidates through replacement. The ordinary library Preview, Apply, player queue and pending edits keep their own state.

## How cut positions are decided

**Manual.** Rust stores a cut as an integer audio-frame position on the decoded source. Each output includes its start frame and stops just before its end frame. Adjacent tracks share one boundary. Validate ordering, duplicates, empty segments, overflow and out-of-range times in Rust. The final range ends at the decoded end of the recording. Keep the lead-in and tail visible and included by default, with an explicit choice to mark any unwanted region for exclusion. Do not mix in a resample, fade or normalization unless the user deliberately requests that processing in a later feature.

**CUE.** Start with external, single-audio-file sheets, including UTF-8 and BOM variants. Offer an explicit encoding choice for legacy sheets rather than guessing. Resolve the named audio against the master selected by the user, and require confirmation if the name differs. Treat sheet paths as data. Do not grant the sheet access to other files. Read `INDEX 01` as the track start and keep `INDEX 00` as source-audio pregap information. A pregap stays at the end of the previous track when splitting at track starts. Moving a track start leaves its pregap start anchored to the original audio and flags it if the edit puts it outside the preceding interval. A lead-in before the first track is visible and requires an explicit export disposition. Show generated `PREGAP` or `POSTGAP` instructions and preserve them in the sheet model where possible. Insert no synthetic silence in the first audio exporter. Flag multi-file, mixed data/audio, malformed and unsupported sheets before export. Keep original CUE frame values for untouched markers. Use checked rational arithmetic on absolute positions and round to the nearest representable frame, with ties forward. Warn when an exact draft cut needs CUE rounding and refuse an export when separate cuts round to the same position. A CUE over one master describes track starts. If it cannot express an excluded region, explain the mismatch and keep the exact draft available alongside the audio export option. The existing CUE export from already-split files stays available. [CUE timing and pregap reference](https://libcdio.github.io/libcdio.html)

**Discogs.** Use the existing authenticated lookup for the specific edition. Keep the release ID, provider order, raw track positions, section headings and whether a length is present. Validate the original duration before the current provider parser can normalize or discard it. Let the user anchor each side or contiguous track range separately in one recording. Show a tape flip as an unassigned region so a missing length on side A cannot shift side B. If one length is missing, stop proposing cumulative cuts at that point and allow a later manual anchor. Treat headings, medleys, nested tracks and aggregate durations explicitly so lengths are never added twice. Compare the release list against the proposed cuts before importing. Keep incomplete or uncertain regions editable, show the difference from the measured recording length, and keep any alignment or replacement of cuts an explicit edit. The source audio stays local. Store the user's edited draft separately from the provider response. Retain only the permitted metadata and provenance. [Discogs tracklist guidance](https://support.discogs.com/hc/en-us/articles/360005055373-Database-Guidelines-12-Tracklisting) · [API terms](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use)

## Shared Rust processing

- Use one Rust module to prepare, review and execute an audio job. The whole-file conversion case is one range over an entire source. A split is several ranges from that source. Keep source identity, exact ranges, tag precedence, destination validation, output capability checks, verification and progress behind that interface. The Svelte code handles the editor, responsive drawing and local pointer feedback. Rust owns decoding, peaks, playback, timing, provider data, tagging, encoding, cancellation and output writes.
- Reuse the current bounded worker and stale-result patterns. Give waveform work, playback and export independent jobs with resource limits. Keep one audio-device owner. Use a scoped preview in the existing Rust player where possible, with ownership checks to ignore stale position and seek replies. Keep preview audio out of the ordinary play queue and media-session history. Restore an earlier playback context only while the preview still owns it.
- **Day-one release requirement.** Open, draw, audition and split MP3, WAV, AIFF and FLAC recordings. Export MP3 and FLAC for both split tracks and whole-file conversion. MP3 input must handle ordinary constant- and variable-bitrate files. Verify encoder delay, padding, output timing and ID3 tags and artwork. Make frame copying the default when splitting MP3 or FLAC to the same format. Offer exact re-encoding and show any changes to the cut position, precision, channels or sample rate in review. Preserve uninterrupted audio across lossless joins. Add WAV output and M4A input after the first release.
- Prove a Rust-native MP3 encoder in the initial experiment with bounded memory, acceptable audio quality, accurate duration and independent playback and tag readback. Compare with FFmpeg as a development reference. The intended shipped path is native Rust. If the native candidates cannot meet the MP3 requirements, settle the codec choice before implementation proceeds. A Rust-managed external encoder would require an explicit exception and pinned builds, licence and source obligations, platform packaging, and installer tests. MP3 remains a release gate either way. [Existing decoder dependency](../../crates/commands/Cargo.toml) · [Rust MP3 encoder candidate](https://docs.rs/shine-rs/latest/shine_rs/) · [FFmpeg distribution obligations](https://ffmpeg.org/legal.html)
- Bind export to the exact revision reviewed in Rust, including source identity, markers, resolved tags, paths and format settings. Hold the verified source open and detect changes before reading and before publication, or use a verified snapshot if the source cannot be kept stable. A stale review, source or destination goes back to review. Read the master sequentially and switch encoders at cut boundaries. Stream outputs to private storage on the destination volume, apply existing tag policies, then verify audio and supported fields by reopening the files. Check for enough space to hold staging files and report an oversized WAV before processing unless its large-file variant is supported. Reserve destination names, detect name collisions and path aliases, and refuse to overwrite an existing file. Reuse the hardened output ownership and no-clobber mechanisms where they fit. The current bounded byte-vector export API is designed for small files, so audio needs a streaming method with the same ownership guarantees. [Current output interface](../../crates/commands/src/output.rs#L310)
- For a split, export into a newly named set folder. Verify all tracks before making the folder visible, using an exclusive same-volume publication method proved on each supported platform. If a platform or filesystem cannot guarantee that claim, fail safely. On Stop before publication, keep the source and destination intact and remove owned in-progress output, or show a recovery location if safe cleanup is impossible. Report a completed set if it already crossed the publication point. An interrupted whole-file batch can retain its individually verified completed files. Avoid promising successful recovery after power loss or on a NAS until tested. Reuse the same outcome and progress model for future conversion. The first release shows the output folder and offers to add completed tracks to the library. The original row remains until the user explicitly changes it.

## Keeping the waveform fast

Build min/max peaks in Rust at several resolutions. Display a coarse view as soon as it is available, then request the finer visible tiles as the user zooms. Cache by verified source identity and resolution with fixed limits. Draw the waveform in a canvas and update the playhead and drag overlay independently once per display frame. Paint the new playhead or marker position locally while dragging, coalesce preview requests, and have Rust confirm the exact frame when the edit settles. Send only visible peaks in compact typed blocks. Measure Tauri's binary transport on our locked version and on each native webview before selecting it. Never ship raw audio to Svelte for analysis or store a decoded recording in webview memory. [Tauri binary IPC](https://v2.tauri.app/reference/javascript/api/namespacecore/)

Provisional targets on a documented reference machine using local 90-minute and three-hour fixtures:

- At 60 Hz, pointer-to-visible playhead or marker movement at or below 33 ms for 95% of samples. Track missed frames as well as the percentile.
- Preview seek to audible sound within 150 ms at the 95th percentile for the admitted local formats. Measure on both cold and warm seeks. Prove the final seek wins during a burst.
- First useful waveform view within one second for cached or progressive local cases. Report full-build time separately by format and recording length. Track peak memory, peak-cache bytes and IPC traffic against an explicit cap before accepting the architecture.
- Keep the main library usable while peaks or export are running. Test when both jobs overlap, with disk pressure and in a narrow, high-DPI window. Measure input-to-paint, the native job and IPC separately to identify the bottleneck. These are targets, not measured app performance.

## Implemented format and verification notes

Same-format MP3 and FLAC splits default to copying the original encoded audio. Review shows each cut moved to a nearby frame boundary and lets the user audition the reviewed position. **Re-encode for exact cuts** keeps the sample position chosen in the editor. Format conversion also encodes the output. Both methods write the reviewed tags and artwork and use the same staged publication rules.

Copy mode rebuilds the timing metadata for each file. It keeps FLAC's compressed audio blocks and MP3's encoded audio frames. MP3 uses a short, trimmed lead-in where needed to restore decoder context. Players that ignore gapless tags can play some extra audio at a cut. Cuts that resolve to the same frame require more spacing or exact re-encoding.

| Operation | First-version support |
| --- | --- |
| Open, preview and split | Constant- and variable-bitrate MP3, FLAC, PCM WAV, and PCM AIFF including SSND padding. Compressed AIFF variants depend on the underlying PCM codec. |
| Copy MP3 or FLAC | Keeps the source codec, encoded audio, channel layout and sample rate. FLAC also keeps its original sample precision. |
| Encode MP3 | Mono or stereo at a standard MPEG sample rate from 8 to 48 kHz. The bitrate is a target for the streaming variable-bitrate encoder. At sample rates below 32 kHz the editor defaults to 128 kbps and offers up to 160 kbps. |
| Encode FLAC | One to eight channels at supported rates up to 96 kHz. Integer inputs from 8 to 24 bits keep their sample precision, widening to the next supported FLAC width where necessary. MP3 and floating-point inputs use 24-bit FLAC storage. |
| Whole recordings | A conversion uses the same review and verification as a split. Save beside the originals, replace them with a recovery copy, or save into a named set in a different folder. For same-format conversion beside the source, the default name adds “Converted” so the two paths are distinct. |
| Library updates | Replacement selects the new rows in an open recursive library or dropped file set. Unrelated edits, selection and view settings remain available. Ordinary exports inside an open recursive library can be added from the completion screen. |

### Save and restore

The waveform and track list are in the Cut step. Review & save starts with the source folder and the reviewed filenames. It shows shifted cuts and their audition controls. The Output options disclosure contains format, encoding method, bitrate and naming options as applicable. CUE and Discogs share the Import cuts menu. A track title can be edited inline with F2.

Replacement verifies the new audio and tags, creates byte-verified backups, and writes a recovery manifest before retiring a source. The default recovery folder is in the app's data directory. Another folder can be selected, including a separate volume. Review refuses a backup folder inside the open recursive library. Undo restores the original files, keeps the generated files in recovery, and removes an empty split folder only while it can still verify ownership. The Undo button belongs to the completion screen. The original backup and the path manifest remain available after closing the editor or restarting the app.

Linux desktop verification used a disposable MP3 in both a recursive library and a dropped file set. After replacement, the two new rows were selected and an unrelated FLAC remained byte-identical. The backup SHA-256 matched the original, and FFmpeg decoded both tracks to the same audio as the original when joined. Undo restored the original hash and the table row. In the dropped-file proof, both new tracks stayed in recovery and the empty split folder was removed. Linux guard tests also cover conflicting files, changed originals, partial retirement, and a separate backup volume.

### Waveform navigation and timing

Wheel zoom accumulates input into a target range and eases toward it while keeping the point under the pointer fixed. Shift-scroll and the draggable or keyboard-operated overview pan the viewport. Wheel zoom, Fit and Zoom to cut apply immediately when reduced motion is enabled. A held drag keeps control as it crosses other parts of the editor, even if the renderer drops pointer capture. Dragging a cut shows its exact time. Escape cancels the gesture, and a committed drag creates one draft Undo step.

The overview and detail canvases repaint independently. The detail view draws coarse and cached peaks in their original positions while it waits for the current higher-resolution tile. A nearby pan can reuse part of the previous result. Playback keeps the requested position while Rust buffers, then discards status replies from earlier commands.

On Linux, a warm 90-minute synthetic MP3 benchmark measured 28 positions in the last third of the file. At the 95th percentile, Rust reached the first preview audio block in 0.50 ms with the sparse MP3 seek index and 27.44 ms with prefix scanning. One-second detail peak calculations took 2.32 ms and 26.95 ms respectively. Building and validating the optional index added about half a second to the opening scan on that fixture. Indexed PCM matched sequential decoding on the reference inputs. These measurements cover Rust processing and exclude webview presentation and audio-device delay.

In the Linux desktop seek check on a separate synthetic 90-minute MP3, the editor received the verified timeline after 13.1 seconds. Preview reported ready at 91% of the recording in 42 ms, and the playhead advanced.

macOS and Windows native webviews and installed packages still require the platform gates. The guarded output workflow includes audio changes and exercises the volume boundary on disposable filesystems. The first cold waveform appears while exact analysis runs. Editing and playback are enabled when that exact timeline is ready.
